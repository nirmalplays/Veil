What Veil is

Veil puts a private AI assistant on any website, and lets anyone check three things instead of taking them on trust:

  • The hardware. Messages are encrypted in the visitor's browser to a key that lives inside an Intel TDX enclave with NVIDIA GPUs in confidential mode. The browser verifies the hardware's attestation before it encrypts anything.
  • The rules. The site's master prompt and its checkable rules are fingerprinted (SHA-256) and registered on NEAR. If the rules a site serves don't match, the chat switches itself off.
  • Every answer. The enclave signs hashes of the exact request and response bytes. An opt-in receipt lets anyone confirm an answer came from that enclave under those rules.

There are four pieces: the widget (one script on the site), the site's relay (a small server that holds the NEAR AI API key and forwards ciphertext), the contract on NEAR testnet (veil-31da02.testnet), and NEAR AI Cloud, where the model runs in a TEE.

Fastest way to understand it: open the live view and press Replay. All ten steps play out with their real values.

Chatting on a Veil site

Click the chat bubble. Before you can type, the widget fetches the site's rules from its relay and compares their fingerprint with the one on NEAR. If they don't match, or the site never registered them, the chat stays off and tells you why.

When you send your first message, the widget asks the model's enclave for a fresh hardware attestation and verifies it in your browser. That takes a few seconds. Later messages reuse the verified key.

"How is this private?"

The button under the chat opens what was checked, with a ✓ or ✗ per line:

LineWhat it means
Policy hash … matchesThe rules served to you are the ones registered on NEAR, and when they were registered.
Every reply is checked against these rulesRules a program can test: word limit, required or forbidden text, patterns. A reply that breaks one is hidden.
Enclave: Intel confirms…, NVIDIA confirms…The hardware checks, listed one by one. See what each check proves.
Knowledge base: fingerprint …The documents the site's AI answers from rebuild the fingerprint registered on NEAR.
Relay: not checked / not in a TEEPress "Check the relay". Ordinary hosting answers "not in a TEE": its operator could read the site's API key, but not your messages.

Receipts

If the site allows them, tick Allow receipts. Answers you get while it's ticked get a Get receipt button. A receipt can be saved two ways:

  • Save proof proves the exchange happened, without revealing what was said.
  • Save with content also includes the one-time keys, so whoever you give it to can decrypt your question and the answer and check them against the signed bytes.

Receipts live in memory only. Unticking the box, or closing the tab, wipes them.

Add Veil to your site

Four steps. The first two happen in the Veil app, which you run on your own machine.

  1. Write your workspace. Name, greeting, the instructions for the AI, and the rules every reply must pass. The Workspaces tab has a tester for sample replies.
  2. Publish to NEAR. One click registers the fingerprint on the contract and makes your account the owner of the site id. Old versions stay on chain.
  3. Host a relay that serves your workspace and holds your NEAR AI key. Free on Render.
  4. Paste the widget into your pages. Build the tag below.
Run the app locally (Node 22)
git clone https://github.com/nirmalplays/Veil.git && cd Veil
npm run setup      # installs client, web and widget
npm run demo       # opens the app at http://localhost:5173/#/app

In the app: Create inline wallet (a funded testnet account), Sign in with NEP-413, then open Workspaces. When you're done, Download site.json.

Host the relay (free)

The relay is a small Node server in widget/relay.ts. It exists because a website can't hide an API key in browser code. It refuses any chat that isn't end-to-end encrypted, never rewrites a request (the enclave signs the exact bytes), and serves many sites at /s/<siteId>/.

Build and publish the image
# copy your site.json into widget/sites/, add a COPY line for it in widget/Dockerfile, then:
docker build -f widget/Dockerfile -t <you>/veil-relay .
docker push <you>/veil-relay
  1. On Render: New → Web Service → Existing image, enter docker.io/<you>/veil-relay, instance type Free.
  2. Add environment variables: NEARAI_API_KEY (from cloud.near.ai), plus random SEAL_SECRET and AUDIT_TOKEN if you use a sealed knowledge base.
  3. Deploy. Check https://<service>.onrender.com/s/<siteId>/config returns your site.
Free hosting sleeps. After 15 idle minutes the next visitor waits up to a minute while it wakes. And it isn't a TEE: the host could read your API key, never your visitors' messages. The widget tells visitors this honestly.

Embed the widget

Fill these in and copy the tag. Host veil-widget.js (from npm run widget:build) next to your pages.

The widget sets no cookies and stores nothing. Its data-rpc attribute takes a comma-separated list of NEAR RPC URLs if you want to choose them.

Lock it to your domain

By default any website can embed your relay and spend your NEAR AI credit (a per-visitor limit of 20 requests a minute applies). Add your origins to site.json:

site.json
"allowedOrigins": ["https://www.example.com"],
"ratePerMinute": 20,
"maxTokens": 3000

Rules a program can check

Rules are part of the fingerprint on NEAR, and the widget runs them on every reply. A reply that breaks one is hidden and replaced by your fallback text, but its receipt still proves what the model said. Tone and judgement can't be written as rules, so "never give legal advice" in the prompt is sent, not proven.

Rule testerRuns Veil's real rule checker in your browser.
    TypeFieldsPasses when
    max_wordsnThe reply has at most n words.
    must_includetextThe text appears (case-insensitive).
    must_not_includetextThe text never appears.
    must_not_matchpattern, labelThe regular expression never matches.

    Knowledge base

    A workspace can carry its own documents. They're split into passages and hashed into a Merkle tree whose root sits inside the registered policy, so changing one passage means a new registered version. Pick a mode in the Workspaces tab:

    ModeWho can read the passagesSearch
    Public, keywordAnyone: the relay serves them and the browser checks the root.BM25 in the browser.
    Public, semanticAnyone. Vectors are covered by the root too.Questions embedded in an attested TEE, ranked in the browser.
    SealedOnly the enclave. The relay encrypts the whole base to the verified enclave key.None: the model reads all of it.
    Sealed means "not published", not "secret". A visitor can still try to coax the model into repeating it; your rules limit how much one reply can say. The owner can prove what was sealed in a request with POST /s/<site>/audit and the AUDIT_TOKEN.

    Verify a receipt

    A receipt holds the exact request and response bodies, the enclave's signature, the attestation report with its nonce, and the policy fingerprint. Verifying one checks:

    1. The signed text is model:sha256(request):sha256(response), and both hashes match the bodies in the receipt.
    2. The ed25519 signature is valid, and the signing key is the one the attestation binds to the enclave.
    3. With content disclosed: the reply decrypts from the signed response, the prompt matches the signed request, and the policy matches the fingerprint registered on NEAR. Then every rule is re-run.

    Two verdicts come out separately: authentic (it really went through the enclave) and obeyed the rules. In the Veil app, open the Receipts tab and drop the file in; the live view's Download the receipt gives you one to try.

    What each hardware check proves

    CheckProves
    Our fresh nonce is echoedThe proof was made just now, for this request. It isn't a replay.
    Intel confirms the quoteThe quote's certificate chain leads to Intel and the platform's security patches are current (TCB UpToDate or SWHardeningNeeded).
    Not in debug modeNobody can inspect the enclave's memory with a debugger.
    Quote binds the key and nonceThe encryption key you're about to use was generated inside this exact enclave.
    Event log replays to RTMR3The boot log is authentic, so the app and compose it names are what actually started.
    Compose matches MRCONFIGIDThe container configuration served with the report is the one the hardware measured.
    NVIDIA confirms the GPUsEvery GPU is genuine, in confidential mode, with secure boot on and debug off. Each GPU's token is checked, not just the overall verdict.
    Gateway checksThe same proofs for NEAR AI's gateway in front of the model.
    Build provenanceNot verified. The image digests are listed so you can look them up on Sigstore.

    Trust model

    • You check: the enclave's hardware attestation, the registered policy fingerprint, knowledge-base fingerprints, and every receipt's signature.
    • You rely on: Intel's and NVIDIA's hardware, NEAR AI Cloud's published enclave images, and the site owner's relay for the API key.
    • Not claimed: no zero-knowledge proofs, no "zero data leakage". The relay sees metadata: time, IP address and message size. The contract is on testnet.

    Troubleshooting

    The chat says "Cannot reach the relay"

    The relay is down or asleep. Free hosting takes up to a minute to wake; reload after that. Check /config on the relay in a browser tab.

    "This site's policy does not match the one registered on NEAR"

    The relay serves a different site.json from the one you published. Publish the current version from the Workspaces tab, or redeploy the relay with the published file.

    "This site has not registered its policy"

    Publish it to NEAR from the Workspaces tab. For local testing only, add data-allow-unregistered="true".

    403 "origin not allowed"

    The page's origin isn't in allowedOrigins. Add it exactly, scheme included, with no trailing slash.

    429 "slow down"

    The per-visitor limit was hit. Raise ratePerMinute if real visitors need more.

    "attestation verification failed"

    A hardware check failed, so nothing was sent. The privacy panel or the live view's log names which check. Try again; if it persists, the enclave may be mid-update.
